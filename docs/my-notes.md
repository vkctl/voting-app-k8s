# Phase 0 Notes — Understanding `example-voting-app`

## Services (6 total)

| Service | Role | Ports | Networks | Depends on |
|---|---|---|---|---|
| `vote` | Python web app — casts a vote, pushes it to Redis | container `80` → host `8080` | `front-tier`, `back-tier` | `redis`, `db` (healthy) |
| `worker` | Pulls votes from Redis, writes them to Postgres | — (no exposed port) | `back-tier` | `redis`, `db` (healthy) |
| `result` | Polls Postgres every ~1s, broadcasts results to all connected Socket.IO clients | container `80` → host `8081` | `front-tier`, `back-tier` | `db` |
| `redis` | Queue — holds votes between `vote` and `worker` | internal only | `back-tier` | — |
| `db` | Postgres — stores votes | internal only | `back-tier` | — |
| `seed-data` | Load-testing helper (Apache Bench) that simulates concurrent votes against `vote` | — | — | not part of the runtime request path |

## Request Flow

```
vote (pushes to redis) → redis → worker (pops from redis, writes to db) → db → result (polls db, pushes via socket.io)
```

## How `worker` reads from Redis

`worker` runs a loop roughly every 100ms doing an async `LPOP` (list-pop) against the votes list in Redis, then attempts an insert into Postgres. If the insert fails because a row already exists for that voter, it falls back to an update.

**Why this is safe for scaling `worker` to multiple replicas:** Redis is single-threaded, so `LPOP` is atomic — if two `worker` replicas pop at nearly the same instant, Redis guarantees each pop returns a *different* item (or nothing). There's no race where two workers process the same vote. This means `worker` can safely run as N replicas polling the same list, with votes distributed across them.

**What the duplicate-handling logic is actually for:** it's not a concurrency safeguard — it's business logic. A voter can change their vote; when they do, a new message lands in Redis for a voter who already has a row in `db`. The insert-fails-so-fall-back-to-update pattern is how `worker` handles "this voter already voted, overwrite their choice" (one voter, two votes over time), not "two workers, one vote, at the same time." Worth keeping this distinction clear.

*Side note for later (not urgent):* catching an insert exception to trigger an update works, but Postgres's `INSERT ... ON CONFLICT DO UPDATE` (upsert) is the cleaner way to express this — avoids using exception handling as normal control flow. Something to consider if this service ever gets touched.

## Scaling Assessment

| Service | Scalable? | Reasoning |
|---|---|---|
| `vote` | ✅ Yes | Stateless, straightforward horizontal scaling |
| `redis` | ⚠️ Partially | Can run primary + replica for HA/failover, but this isn't a sharding/throughput win — it's a simple queue, not a scaled dataset |
| `worker` | ✅ Yes | Confirmed safe — Redis `LPOP` atomicity prevents double-processing across replicas |
| `result` | ⚠️ Yes, with a cost | Each replica runs its own independent 1s polling loop against `db`. Scaling `result` to N replicas means N× the DB read load, not free horizontal scaling. This is the concrete case for adding a pub/sub layer later (Phase 8) so replicas don't each hit the DB independently. |
| `db` | ✅ Yes, but not via HPA | 1 primary (writes) + read-only replicas. Replica count is a deliberate infra decision, never a reactive autoscale — spinning up a new replica requires a full base backup. |

## Phase 3/4 — Local Kubernetes Deployment (summary)

Set up a local `kind` cluster and deployed all 5 services one at a time (redis → db → worker → vote → result), writing each manifest only after actually confirming how that service connects to its dependencies — this caught real things I'd have gotten wrong otherwise: `worker`, `vote`, and `result` all have hardcoded hostnames (`redis`, `db`) and hardcoded db credentials rather than reading env vars, and `result`'s listening port (`80`) isn't obvious from its own code — it's baked into its Dockerfile via `ENV PORT`, not visible in `docker-compose.yml` or `server.js` alone. Along the way, learned the core building blocks: Pods (disposable, managed via Deployments), Services (stable DNS name routing to whichever Pods are currently healthy, linked only via label matching), Secrets (base64-encoded, not encrypted — fine for now, needs real handling before AWS), PersistentVolumeClaims (only `db` needs one, since losing votes on restart would defeat the point), and Namespaces (organizational partitioning, not a security boundary by default).

Getting real browser access (rather than temporary `kubectl port-forward` tunnels) required installing an Ingress controller (`ingress-nginx`) and recreating the kind cluster with a config exposing ports 80/443 to the host — a good live example of "destroy and recreate fast" since the whole app came back in one `kubectl apply -f k8s/base/` command afterward. Final result: `vote.local` and `result.local` (via a hosts-file edit) route through one Ingress to the two front-facing services, and the full vote → redis → worker → db → result pipeline works end to end on a real (local) Kubernetes cluster.

## Phase 3 — AWS + Terraform (summary)

Moved to real AWS after getting comfortable on local kind — used an IAM user (not root) with access keys, `aws configure` to connect the CLI, then wrote Terraform incrementally, one piece at a time, reading every `plan` before applying: **networking** (VPC, 2 public subnets across 2 AZs — skipped NAT Gateways deliberately for speed/cost, accepting the trade-off of nodes having public IPs), **IAM roles** (two separate "badges" — a trust policy answering "who can assume this role" plus attached AWS-managed permission policies answering "what can it do once assumed" — one role for the EKS control plane, one for worker nodes), the **EKS cluster** itself (the managed control plane, ~$0.10/hr, took ~6 minutes to create), and the **node group** (the actual EC2 worker machines).

Considered using **AWS VPC IPAM** (hierarchical, structured CIDR allocation by environment/region/workload) instead of a hardcoded CIDR block — legitimate and used at real scale, but decided against it for this project specifically: provisioning a CIDR through IPAM can take up to 30 minutes and complicates teardown ordering, directly working against the "destroy/recreate fast" goal. Filed away as something to learn separately later, not inside this fast-iterating project.

**Real mistakes made and fixed, worth remembering:**
- Typo'd an EKS subnet discovery tag (`kubernetes.io/clusters/...` instead of `kubernetes.io/cluster/...`, singular) — Terraform didn't warn, because `tags` is just a generic string map to it; it has no idea AWS's own systems search for that exact key elsewhere. Same category of bug as the earlier `packages: write` GitHub Actions typo — syntactically valid, semantically wrong, nothing downstream flags it.
- First node group attempt used `t3.medium`, which failed with `InvalidParameterCombination` — the AWS account has **Free Tier usage restrictions** enabled, blocking any non-free-tier instance type. Not a capacity issue — an intentional account guardrail. Fixed by switching to `t3.micro` rather than disabling the restriction, since disabling it would remove a protection aligned with this project's own budget-consciousness.
- That failed node group got marked **"tainted"** by Terraform (created in AWS but never finished successfully) — Terraform's safe response to a tainted resource is destroy-then-recreate rather than trying to patch a half-built resource. The cleanup of that broken node group took ~16 minutes — notably slower than creating a clean one (~2 minutes) — a reminder that failure-path teardown isn't always as fast as the happy path, worth expecting rather than panicking over.

**Other concepts learned along the way:** `depends_on` (for ordering Terraform can't infer just from references — e.g. IAM policy attachments needing to exist before the cluster/node group that relies on them), Terraform automatically refreshing/diffing state against real AWS on every `plan`/`apply` (drift detection that only runs when explicitly invoked — not continuous, which is exactly the gap Argo CD is about to fill), and the distinction between node-group scaling (how many *machines* exist) versus Horizontal Pod Autoscaling (how many *Pod replicas* run) — two separate layers that both matter once real scaling work starts.

Next: destroy this environment cleanly, confirm it in the AWS console, then rebuild via `terraform apply` to prove the fast recreate loop — the actual reason all of this was built to be destroyable from day one.

## Phase 3 continued — Terraform deploys the app itself

Destroyed and recreated cleanly (confirmed the fast rebuild loop works — ~10 minutes for the full cluster from scratch). Then split Terraform into two separate configs, `cluster/` and `app/`, after hitting a real bug: the `kubernetes`/`helm` providers, when configured using a *direct resource reference* to the cluster being created in the same run (`aws_eks_cluster.main.endpoint`), silently fell back to `localhost` instead of the real cluster — a documented chicken-and-egg provider-timing issue. Fixed by having `app/` use `data` source *lookups* ("find the cluster that already exists") instead of resource references, which resolved cleanly every time after.

Translated the Kubernetes manifests from the kind phase into native Terraform HCL (`kubernetes_deployment_v1`, `kubernetes_service_v1`, etc.) — same concepts, same tree shape, different syntax. `redis` first (simplest), confirming the whole provider chain worked before anything else depended on it.

**PVC support on EKS needed real setup, unlike kind's automatic `local-path-provisioner`:** required IRSA (IAM Roles for Service Accounts) — a narrower kind of IAM role than the node role, trusted only by a specific Kubernetes ServiceAccount via an OIDC identity provider registered against the cluster, rather than trusted by "any EC2 instance." Three pieces: the OIDC provider itself, the IAM role with that narrow trust policy, and installing the EBS CSI driver addon wearing that role. Chose `Delete` reclaim policy over `Retain` for the PVC's StorageClass — deliberately, since `Retain` would leave orphaned (still-billed) EBS volumes behind on every destroy, directly fighting the project's "destroy fast" goal, for data (vote counts) not worth protecting.

**Real bugs hit and fixed in this stretch:**
- `db`'s PVC deadlocked against its own Deployment: the StorageClass used `WaitForFirstConsumer` (correctly waits for a real Pod before creating the EBS volume, so it lands in the right AZ) — but Terraform's PVC resource defaults to waiting for `Bound` before creating anything that depends on it, including the very Deployment whose Pod would trigger binding. Fixed with `wait_until_bound = false` on the PVC.
- Postgres then failed to start with `initdb: directory exists but is not empty` — every freshly formatted EBS volume's ext4 filesystem includes a `lost+found` directory at its root, which `initdb` refuses to treat as empty. Fixed by pointing `PGDATA` at a subdirectory of the mount rather than the mount root itself.
- `t3.micro` nodes hit a hard pod-density ceiling (max 4 pods/node — a real AWS formula based on ENI/IP capacity, not a bug) — mandatory system Pods alone filled both nodes completely, leaving zero room for the EBS CSI controller or any app Pod. Fixed by moving to `t3.small` (11 pods/node), confirmed free-tier eligible for accounts created after July 2025 — initially assumed otherwise and was corrected.
- The `helm` provider failed with "cluster unreachable" — turned out to be a genuinely missing kubernetes auth block in that provider's config, not a provider-timing bug as first suspected. Worth remembering: check for the boring explanation before the exotic one, even when a symptom resembles a bug seen before.
- Path-based Ingress routing (`/vote`, `/result` on one shared Load Balancer) broke both apps' JS/CSS: their HTML references assets via *absolute* paths, which a path-rewrite can't retroactively fix inside already-served HTML. Fixed by giving `vote` and `result` each their own `type: LoadBalancer` Service instead — simpler and more reliable than chasing host-based routing via a Load Balancer's non-static IP, at the cost of a second small Load Balancer charge.

**Other real concepts learned:** IRSA vs. node-level IAM roles (workload-specific badge vs. shared node badge), Terraform's `helm_release` resource as a higher level of abstraction than raw HCL resources (delegates real complexity to a published chart), image tag passed as a Terraform *variable* (`-var="worker_image_tag=<sha>"`) rather than hardcoded — a build-once, promote-via-variable pattern common in real CI/CD pipelines — and `ImplementationSpecific` path types marking controller-specific (non-portable) Ingress behavior.

Whole app now running end-to-end on real AWS, fully provisioned via Terraform. Next: deliberately drift something on this live cluster and watch Terraform fail to notice, then bring in Argo CD.

## Phase 6 — Argo CD (summary)

**First drift test, on the `app/` Terraform stack:** manually `kubectl scale deployment vote --replicas=3`, simulating an unplanned hotfix. `terraform plan` genuinely *did* detect it (`replicas: "3" -> "1"`) — the real gap wasn't "Terraform is blind to drift," it was "Terraform only checks when a human remembers to run it." Confirmed the sharper edge of that: running `terraform apply` silently reverted the manual scale-up back to 1, with no awareness it might have been there for a real, current reason. This was flagged as not a fully honest demo of Argo CD's value on its own — a fair pushback — since it only showed Terraform doing its normal job.

**The actual fair comparison: delete a live resource outright (`kubectl delete service vote`) and simply don't fix it.** With nothing watching (Terraform-managed at the time), the outage stayed broken indefinitely — however long it took a human to notice and act, no different from zero tooling at all.

**Moved `vote` to Argo CD to rerun the same test properly:**
- Deliberately handed over one resource at a time rather than migrating everything at once — Argo CD syncs from plain YAML in git (has no concept of Terraform/HCL), so `vote` was rewritten as a manifest matching the *already-running* Terraform version exactly (same name/namespace/labels) so Argo CD would adopt the live object instead of creating a duplicate — Kubernetes identifies resources by name+namespace+kind, not by which tool created them.
- Removed `vote` from Terraform's state (`terraform state rm`, then deleted its resource blocks) — necessary so Terraform and Argo CD stop fighting over the same object. Deliberately chose to leave the rest of `app/`'s resources (redis, db, worker, result) untouched for demonstration purposes, and decided not to run `terraform apply`/`destroy` in `app/` going forward — with one necessary exception: `app/` still needs a `terraform destroy` *before* `cluster/`'s, since `vote`/`result`'s `LoadBalancer` Services have real AWS ELBs behind them that won't get cleaned up if the cluster disappears first — a real orphaned-cost risk, not just a tidiness concern.
- Installed Argo CD itself via a **separate** Terraform directory (`argocd/`), reusing the same `data`-source cluster-lookup pattern from `app/`'s provider fix, rather than touching the frozen `app/` config.
- Created an Argo CD `Application` resource (via `kubernetes_manifest`, since Argo CD's CRDs aren't natively typed by the kubernetes provider) pointing at `k8s/argocd/`, with `syncPolicy.automated.selfHeal: true` — the actual setting that makes self-healing happen automatically rather than just flagging drift for a human to approve.
- Brought all 5 services under the same `Application` at once by adding their manifests to the same watched directory — no need for 5 separate `Application` resources, since one `source.path` pointing at a directory syncs everything under it.

**Real bug hit:** `db`'s PVC failed with `storageclass.storage.k8s.io "ebs-gp3" not found` — the StorageClass still only existed in the frozen `app/` Terraform stack, not in anything Argo CD was managing, so `db`'s new dependency pointed at something outside its own source of truth. Fixed by adding the StorageClass as its own Argo CD-managed manifest too — the general lesson: everything a resource depends on needs to live in the *same* system of record, or the split becomes a hidden source of exactly this kind of breakage.

**The actual rematch, run for real:** deleted the `vote` Service again. This time, watched `kubectl get svc -w` and did nothing — Argo CD noticed and recreated it with zero human action, correcting the exact same failure that stayed broken indefinitely under Terraform-only management.

**Important distinction worth not conflating, caught by comparing two different deletions:** deleting a *Pod* and watching it come back is **not** Argo CD — that's core Kubernetes' own Deployment/ReplicaSet controller, which has always continuously reconciled Pod count regardless of Argo CD's presence. Deleting a *Service* and watching it come back **is** genuinely Argo CD — Kubernetes has no native controller that notices a deleted Service and recreates it; that gap (drift at any level, corrected continuously, without a human ever running a command) is the specific, real thing Argo CD adds. Terraform can also fix that same drift, but only reactively, whenever someone happens to remember to run `apply` — the actual difference is continuous+automatic vs. correct-but-only-on-request.

## Phase 6 continued — Clean teardown

Before destroying, `app/` had already been destroyed earlier and never rebuilt — everything running (all 5 services, the StorageClass) was created directly by Argo CD from `k8s/argocd/` manifests, not adopted from a live Terraform stack. Worth remembering for next time: `selfHeal: true` means a plain `kubectl delete` on anything Argo CD manages gets immediately undone — the same self-healing being celebrated works against you the moment you're the one trying to remove something.

The fix: add the `resources-finalizer.argocd.argoproj.io` finalizer to the `Application` (baked permanently into `argocd-app.tf` now, not just a one-off `kubectl patch`), then `kubectl delete application voting-app -n argocd`. This properly cascade-deletes everything the Application manages *while the cluster is still alive* — critical, since `vote`/`result`'s real AWS ELBs and `db`'s real EBS volume only get cleaned up correctly by controllers running inside the cluster; destroy the cluster first and both would've been orphaned, silently still billing.

Confirmed via `kubectl get svc/pvc/pods` (all empty) and directly in the AWS Console (no lingering Load Balancers or EBS volumes) before proceeding — same "trust but verify" habit as every destroy this project. Then `terraform destroy` in `argocd/`, then `cluster/`, in that order. Full environment confirmed gone, nothing left running or billing.

**End state of this stretch:** the whole 5-service app, deployable from nothing to fully working on real AWS in roughly 10 minutes (cluster) plus a few more minutes (Argo CD + app sync), entirely from files in this repo — genuinely proving the "destroy and recreate with extreme velocity" goal set at the very start of the AWS phase.

## Phase 8 — Autoscaling (summary)

Switched `cluster/` from hand-written raw Terraform resources to the community `terraform-aws-modules` (VPC + EKS + IAM). Real trade-off, made deliberately: less hands-on debugging going forward, but the modules encode a lot of production-grade correctness (KMS secrets encryption, detailed security group rules, least-privilege IAM) the raw version never had. Hit and fixed several genuine module-API surprises mid-migration — `cluster_addons` renamed to `addons`, the IAM submodule path dropped its `-eks` suffix, `role_name` became `name` — confirming a useful general skill: after `terraform init`, a module's *actual downloaded source* (`.terraform/modules/.../variables.tf`) is more reliable than any blog post or guide when APIs are in flux.

Built Karpenter for real node-level autoscaling (distinct from HPA's Pod-level scaling) via the official `terraform-aws-modules/eks/aws//modules/karpenter` submodule — handles controller IAM (via **EKS Pod Identity**, the newer, simpler successor to IRSA: a direct namespace+service-account→role association, no OIDC trust-policy string matching required), a node IAM role/instance profile, and an SQS queue + EventBridge rules for graceful spot-interruption handling, all from one submodule call. Karpenter's CRDs (`NodePool`, `EC2NodeClass`) install via a *separate* Helm chart (`karpenter-crd`) from the controller itself as of Karpenter v1.x — same chicken-and-egg CRD-before-controller ordering issue hit twice before, same `-target` fix.

**Self-directed fix, not something I suggested:** hit the same 11-pods-per-node ceiling from earlier again (now from Karpenter/Argo CD/metrics-server Pods added on top of the original 5 services), and fixed it properly via VPC CNI **prefix delegation** (`ENABLE_PREFIX_DELEGATION`) — assigns whole `/28` IP blocks per ENI instead of one IP at a time, raising the ceiling from 11 to 32 pods/node — plus switched the EBS CSI driver from IRSA to Pod Identity too, for consistency with Karpenter's newer approach.

Installed `metrics-server` (not automatic on EKS, same category as the EBS CSI driver) and added `resources.requests`/`limits` to `vote`/`result` plus `HorizontalPodAutoscaler` resources for both (`autoscaling/v2`, target 50% CPU).

**Load test — real findings, not a clean demo:**
- First traffic-generator version had a real bug: reused one `requests.Session()` per worker thread across its whole phase, meaning every POST from that thread looked like the *same* voter repeatedly changing their vote (the app's own upsert-on-conflict behavior), not a new voter each time. Result: 6820 HTTP requests sent, only ~176 actual votes registered. Fixed by not persisting a session/cookie between requests.
- **HPA fully proven, both directions:** `vote` scaled 1 → 4 → 6 replicas (hit `maxReplicas`) as CPU spiked past 50%, then correctly scaled back to 1 once load stopped.
- **Karpenter did not trigger** — expected, not a failure: the new 32-pod/node ceiling gave far more headroom than 6 replicas needed. Confirms triggering real node-level scaling needs either a much higher `minReplicas`/load, or deliberately smaller per-node capacity for demo purposes.
- **Real anomaly found, not yet root-caused:** `vote` Pods repeatedly cycled through `Error`/`Completed` states during peak load — genuinely unexplained without checking `kubectl logs --previous` and restart counts on `worker`/`redis`/`db`. Also observed vote counts still fluctuating *after* the load test ended, with no active traffic — worth checking whether the generator process was fully stopped and whether `worker`/`redis` restarted mid-test (possible in-flight vote loss/reprocessing from Redis).
- **Confirmed gap surfaced by this investigation: no `readinessProbe`/`livenessProbe` on any of the 5 services.** Without a readiness probe, a Service routes real traffic to a new Pod the instant its container starts — not once the app inside can actually handle a request. Plausible contributor to the crash pattern during HPA scale-up (new Pods getting slammed before fully initialized), though not yet confirmed via actual crash logs — the original `vote` app also uses Flask's built-in dev server (single-threaded/blocking, not meant for real concurrency), a separate possible contributing factor worth remembering distinctly from the probes issue.

Added `readinessProbe`/`livenessProbe` to all 5 services — `vote`/`result` via native `httpGet` (kubelet makes the HTTP call directly, no need to exec `curl` the way the original docker-compose healthcheck did), `redis`/`db` via `exec` calling `redis-cli ping` / `pg_isready` — both already built into their official images, so the original `redis.sh`/`postgres.sh` scripts never needed mounting at all. Two honest, unresolved gaps flagged rather than papered over: `result`'s probe only proves the HTTP server is up, not that `db` is actually reachable (its `/` route serves a static page regardless — a real fix needs a dedicated `/health` route added to `result`'s own source); `worker` has no probe at all, since it has no HTTP port and no `redis-cli`/`psql` client tools in its own (.NET-only) image to exec against — matches a gap that already existed in the original `docker-compose.yml` too, not something newly introduced here.

**Rewrote the traffic generator (own version, not the one I originally wrote)** — fixed-request-count phases via `ThreadPoolExecutor` rather than duration-based, and critically, no persisted session/cookie between requests (the bug that caused the earlier "6820 sent, only 176 registered" mismatch). Clean rerun: ~55,000 total requests across the same 7-phase ramp (5→20→50→100→50→20→5 workers), error rate well under 1% throughout — a genuinely clean, working load test this time.

**Karpenter confirmed triggering for real, on this run** — achieved not by more raw traffic, but by raising per-pod memory *requests* (~110Mi → 200Mi), which pushed memory rather than CPU into being the binding constraint against the 2 existing nodes' capacity, forcing a 3rd node. Confirms the earlier prediction: with the 32-pod/node ceiling from prefix delegation, triggering real node-level scaling needs either much higher replica counts or deliberately tighter per-node headroom — raw request volume alone wasn't enough.

**Genuine architectural bottleneck found by reading `worker`'s actual source, not guessed at:** its main loop does `Thread.Sleep(100)` between each check-and-process cycle, popping and handling **at most one vote per 100ms** — a hard ceiling of ~10 votes/second, regardless of how fast `vote` accepts requests or how many replicas `vote`/`result` scale to (comment in the code says this delay is deliberate, "to prevent CPU spike"). This directly explains why `result`'s numbers kept climbing for a long while *after* the load test itself finished: `vote` (helped by its HPA) could enqueue votes into Redis far faster than single-instance `worker` could ever drain them, building a large backlog that `worker` continued slowly working through long after traffic stopped. `worker` was never included in the autoscaling work — and it's not yet clear whether adding replicas would even help proportionally, since some of that 100ms delay may be deliberate throttling rather than real processing time. This is effectively the same category of problem (a slow, serialized downstream consumer creating latency/backlog under load) the observability phase is specifically meant to trace from symptom → root cause — found here organically through direct load testing, ahead of the planned deliberate version.

**Probes added, using tools already built into the images rather than mounting the original healthcheck scripts:** `vote`/`result` use native `httpGet` probes (kubelet makes the HTTP call itself — no need to exec `curl` the way the original docker-compose healthcheck did); `redis` and `db` use `exec` probes calling `redis-cli ping` and `pg_isready` respectively — both tools already ship in their official images, so the original `redis.sh`/`postgres.sh` scripts never needed to be mounted via ConfigMap at all. Two honest, unresolved gaps: `result`'s probe only proves its HTTP server is up, not that `db` is actually reachable (would need a real `/health` route added to `result`'s own source code); `worker` has no probe at all — no HTTP port, no `redis-cli`/`psql` client tools in its bare .NET image to exec against, and the original `docker-compose.yml` never gave it one either. Both flagged as follow-ups requiring actual application code changes, not just manifest config.

**Rewrote the traffic generator** (fixed request-count phases via `ThreadPoolExecutor`, no shared session — fixing the earlier bug) and reran the full load test at higher volume (~53,000 total requests across the ramp) — **near-zero error rate this time** (well under 0.1%), a big improvement over the earlier crash-heavy run, consistent with (though not definitively proven to be caused by) the new readiness probes now gating traffic to unready Pods. **Also bumped `vote`/`result`'s memory requests from ~110Mi to 200Mi**, and this time **Karpenter actually triggered** — the higher per-Pod memory footprint across 6 HPA-scaled replicas pushed real node capacity, not just pod-count, past the existing 2 nodes' limit, triggering a genuine new node provision. This closes out the full autoscaling stretch goal: HPA (Pod-level) and Karpenter (node-level) both proven working under real, self-generated load, both scaling up and back down.

Next: observability (metrics, logs, traces).

**Probes added, and the hypothesis actually got tested, not just asserted:** `vote`/`redis`/`db` got real readiness+liveness probes using tools already built into their images (`redis-cli ping`, `pg_isready`) rather than mounting the original `redis.sh`/`postgres.sh` scripts via ConfigMap — simpler, same guarantee, nothing extra to maintain. `result` got a weaker, honestly-labeled probe (plain HTTP check on `/`, which does *not* actually verify DB connectivity, since `/` serves a static page regardless) — a real fix would need a dedicated `/health` route added to `result`'s own source code, noted as a follow-up rather than faked. `worker` got no probe at all — it has no HTTP port and no `redis-cli`/`psql` tools in its own .NET runtime image to exec against; the original `docker-compose.yml` never gave it one either, so this isn't a regression, just an existing gap.

Also rewrote the traffic generator (fixed-request-count phases via `ThreadPoolExecutor`, no session/cookie reuse — each request now correctly looks like a distinct voter) and reran the full ramp with more headroom (up to 100 workers / 20,000 requests at peak). Result: **error rate dropped from a chaotic, constantly-crashing pattern to near-zero (9–22 errors out of 10,000–20,000 requests per phase, ~99.9% success)** — strong real evidence the missing readiness probes (new Pods getting traffic before they could handle it) were a genuine contributor to the earlier instability, not just a theory.

**Also deliberately bumped `vote`/`result`'s memory *requests* higher** (reducing how many Pods fit per node before hitting the 32-pod/node ceiling) — this is what finally gave Karpenter a real reason to act, and **it worked**: watching real node-level autoscaling trigger for genuine capacity pressure, not left as an untested "probably works" claim from earlier. Closes Stretch A completely: HPA proven both directions (Pod-level), Karpenter proven triggering for real (node-level), traffic generator reliable and reusable for future load tests.

## Phase 9 — Observability: Metrics (summary)

**Installed `kube-prometheus-stack`** (Prometheus + Alertmanager + Grafana + kube-state-metrics + node-exporter, bundled) via Helm/Terraform in a new dedicated `observability/` directory. One real gotcha: Grafana briefly showed `2/3` ready on first start — just an internal sidecar warming up, resolved itself, not a real problem.

**Instrumented application metrics in all 3 own-code services, one language at a time, checking each Dockerfile's actual production command before assuming anything:**
- **`vote` (Python/Flask):** confirmed production runs `gunicorn --workers 4` — meaning 4 separate OS *processes*, each with private memory. This directly updated an earlier wrong guess: the load-test crash pattern from Phase 8 was more likely caused by these 4 sync workers + `--keep-alive 0` under 100 concurrent connections, not Flask's dev server as first assumed. Found `prom-client` itself is npm-deprecated (superseded by `@prometheus-io/client`) but still functional and hugely used (7.7M weekly downloads) — used it anyway rather than risk guessing at an unverified newer library's API, filed the migration away as a deliberate future follow-up.
- **`worker` (.NET):** the one that actually mattered most for the diagnosis. Confirmed the free bonus of `prometheus-net`'s auto-collected .NET runtime metrics, including `system_runtime_exception_count_total` — real evidence of the expected `DbException` from the insert-then-fallback-to-update pattern, now actually counted rather than just known conceptually.

## Phase 9 continued — Observability: Traces (summary)

**Installed Tempo (single-binary mode, same filesystem-storage reasoning as Loki) and a *second*, separately-configured Alloy instance** dedicated to receiving OTLP traces — a `Deployment` (one stable Service endpoint for apps to push to), not a `DaemonSet` like the log-shipping Alloy. Confirmed Grafana's own official example config (`otelcol.receiver.otlp` → `otelcol.exporter.otlp`) worked as documented.

**Instrumented all 3 own-code services with OpenTelemetry, checking real constraints before assuming a library's default setup would work:**
- **`vote`:** same multiprocess concern as metrics — gunicorn's 4 worker processes mean the OTel SDK also needs setup inside a `post_fork` hook (background span-flush threads don't survive `fork()`, so setting up tracing before the fork would leave only the master process with a working exporter).
- **`worker`:** `StackExchange.Redis` (2.2.4) and `Npgsql` (4.1.9) both predate their libraries' native OTel integration — used manual `ActivitySource` spans instead of auto-instrumentation, the technically honest choice given the real versions in use, not a shortcut.
- **`result`:** Node's auto-instrumentation ecosystem is more mature — covers `pg` and Express for free. The one manual piece: `getVotes()`'s polling loop gets its own deliberately independent **root span** every cycle, not extracted from any vote's context — architecturally correct, since a poll aggregates *all* votes and isn't causally "caused by" any single one.

**The hard, genuinely valuable piece: manual trace-context propagation across the Redis queue boundary**, since `vote`→Redis→`worker` is not a direct call auto-instrumentation can bridge. `vote` injects the current trace context (`propagate.inject()`) into the vote's JSON payload as a `trace_context` field; `worker` extracts it (`Propagators.DefaultTextMapPropagator.Extract`) before starting its own span as a child of that context. This is what let one trace later show a vote's entire journey — `vote` → the Redis wait → `worker`'s `process_vote` → `db_write` — as a single connected timeline.

**Real bugs hit and fixed, several with genuinely misleading error messages:**
- `vote` showed up in Tempo as `unknown_service:python3.11` — the `TracerProvider()` in `gunicorn.conf.py`'s `post_fork` hook was never given a `service.name`, so the SDK fell back to its default. Fixed with `Resource.create({"service.name": "vote"})`.
- `result`'s `tracing.js` crashed on startup: `TypeError: Resource is not a constructor` — a genuine breaking change in `@opentelemetry/resources` v2.x, which removed the `Resource` class entirely in favor of a `resourceFromAttributes()` factory function. Also dropped the `@opentelemetry/semantic-conventions` constant for `service.name` in favor of the plain `'service.name'` string key, since that package renamed several of its own constants in the same migration wave and a second guess at the new name felt riskier than just not needing it.
- `worker`'s spans never reached Tempo at all, with **zero error output** — traced down methodically: confirmed the image was current (DLLs present), confirmed votes were processing, confirmed TCP to the collector was open, confirmed the manifest's env vars synced. The actual cause: **the .NET OTel SDK reports its own export failures to an internal `EventSource`, not stdout** — completely invisible to `kubectl logs` by default. Added a custom `EventListener` (`OtelDiagnosticsListener`) to surface these on stderr — this single fix is what made the real error (`HttpRequestException` on the gRPC/4317 export) visible at all. First fix attempt (moving endpoint/protocol from hardcoded to env-var-driven, matching gRPC on the same port) didn't resolve it; flipping to HTTP/protobuf on port 4318 did — Python's gRPC library and .NET's `HttpClient` evidently handle plain-text HTTP/2 differently, and .NET's didn't complete the call. Also had to filter the new diagnostics listener down to only `OpenTelemetry`-prefixed event sources — subscribing to any source in the process makes .NET deliver *all* listeners' `EventCounters` (including `prometheus-net`'s runtime-metrics adapter) to every listener, which briefly flooded the logs with `System.Runtime`/`System.Net.*` noise unrelated to tracing.

**Confirmed working end-to-end, and the trace told a real story immediately:** a vote cast during a load test showed a 30.98s total trace duration — `vote`'s handler (9ms) and `RPUSH` (5ms) accounted for almost none of it; nearly the entire duration was pure queue wait, `worker` hadn't reached that vote yet. This was the moment `worker_redis_queue_length` (a metric) and a trace (a concrete, individual request's story) told the same fact two different ways — proving the whole three-signal build was coherent, not three disconnected dashboards.

**Wired Tempo into Grafana with trace-to-logs correlation**, matching by `service.name` (honest limitation: none of the three services write their `trace_id` into their actual log lines, so this lands you on roughly the right logs, not a precise jump to one exact line — a real fix needs that added to each service's logging calls, filed as a follow-up).

## Fixed a real circular dependency, found via a full destroy/rebuild

A from-scratch rebuild (after fully destroying overnight) failed in a way incremental builds never had a chance to reveal: Argo CD's manifests (`k8s/argocd/`) include `ServiceMonitor`/`PodMonitor` resources whose CRDs only exist once `observability/` has been applied — but Loki/Tempo's PVCs need the `ebs-gp3` **StorageClass**, which lived *inside* `k8s/argocd/`, meaning it only existed once Argo CD had already synced. Two stacks needing each other to go first, no valid order. Fixed by moving the StorageClass out of Argo CD's management and into Terraform (`karpenter/storageclass.tf`, alongside Karpenter/`metrics-server` as "cluster-wide platform prerequisites") — a stack that runs before both. Correct order now: `cluster/` → `karpenter/` → `observability/` → `argocd/`. Also added `syncOptions = ["SkipDryRunOnMissingResource=true"]` to the `Application` as a second line of defense — lets Argo CD tolerate a CRD that doesn't exist yet and retry on its normal reconcile loop, rather than hard-failing.

**Separately, hit a stuck Argo CD teardown** — `kubernetes_manifest.voting_app` destroy hung for 10+ minutes waiting on the cascade finalizer. Root cause never fully confirmed (likely a resource that couldn't cleanly delete), but the recovery pattern is worth keeping: don't blindly re-run `terraform destroy` and wait blind again — check what's actually stuck first (`kubectl get pods -n argocd`, the Application's conditions, any Services/PVCs with a lingering deletion timestamp). If truly stuck, `kubectl patch application ... --type merge -p '{"metadata":{"finalizers":null}}'` removes the finalizer immediately (Application vanishes, but *without* cascading) — safe only if followed immediately by manually deleting the actual app resources (Deployments first, then Services/PVCs) while the cluster is still alive, so the real AWS ELBs/EBS volumes still get cleaned up properly.

## PromQL, learned properly rather than just copy-pasted

**Staleness, not deletion.** Prometheus never deletes a series when a Pod disappears — data sticks around for the full retention period. What actually happens: once a target stops being scraped (its Pod is gone from service discovery), Prometheus marks that series "stale" after a few minutes. A query anchored at **now** (a live graph, an Instant query) reads that marker and shows nothing for it — but the historical samples are still there. Confused "why did my pod's metrics disappear" — answer: they didn't, the *view* was asking about the present, not the past.

**Instant vs. Range are two different queries feeding two different panels**, not two views of the same data. Range = one point per scrape interval across the whole window (feeds the graph, shows full history). Instant = a single snapshot evaluated at exactly one timestamp — the right edge (`To`) of the time picker — which defaults to "now" but isn't inherently "live"; **setting `To` to a moment in the past turns Instant into a snapshot of that past moment**, which is the direct way to get a specific historical raw-values table without hand-writing the `@` timestamp modifier.

**Three ways to read a counter, and they answer different questions — mixing them up gives confidently wrong numbers:**
- `sum(metric)` — current snapshot values added up. Breaks the moment any contributing series has gone stale (silently under-counts, no error).
- `sum(increase(metric[range]))` — **estimates** growth by computing a rate and extrapolating across the window. Correctly designed for "how fast is this growing," not for exact counts — a real example: `increase()` gave `9125.678417657344` against a real, exact `11000` votes, specifically because the time range was wider than the actual burst, so the extrapolation was partly built from idle time. The non-integer result is itself the tell that something's being estimated, not counted.
- `sum(last_over_time(metric[range]))` — the actually correct tool for "true total including things that no longer exist." Returns each series' real last recorded sample, no extrapolation — landed on the exact `11000`.

**Everything in PromQL reduces to knowing which of four data types you're holding at each step** (instant vector, range vector, scalar, string) and matching that to what the next function expects — range functions (`rate`, `increase`, `*_over_time`) need a `[window]` bracket because they require a *range* vector; aggregations (`sum`, `avg`, `topk`) collapse *series*, a completely different axis from time; binary operations only combine vectors whose label sets actually match (why dividing a labeled gauge by an unlabeled `sum(...)` silently returned nothing — `scalar()` sidesteps this by converting to a bare number with no labels to match against). The same discovery method — check the actual metric/label/help text, don't assume — extends to Loki (label browser + `|= "text"` filters on log streams, since logs have no fixed catalog the way metrics do) and Tempo (Search tab dropdowns, filled from what's actually been ingested; a service only has the spans someone's instrumentation code actually created).

## Onboarding-to-an-unfamiliar-service playbook (a real, generalizable exercise)

Practiced discovering "what does this service expose" as if joining a new team, using `worker` as the specimen: `/metrics` endpoint's `# TYPE`/`# HELP` lines are the app's own declared catalog (though labeled metrics only appear after their first observation — the endpoint is a snapshot, not a complete list); `count by (job, __name__) ({pod=~"worker-.*"})` reveals *everything* Prometheus has about the Pods, including platform-added series (kubelet, kube-state-metrics) the app never wrote itself. Two separate questions hiding under one. Logs have no such catalog at all — the code (`grep` for the actual log calls) is the only complete source, since a stream's labels describe *where* logs come from, not *what* they'll ever say. Traces are stricter still — a service only emits exactly the spans its instrumentation (auto or manual) was written to produce.

**The layered honest answer to "what's guaranteed to be present":** almost nothing is enforced, most of it is convention — platform-generated cluster/Pod metrics and all stdout/stderr logging are the closest thing to "always there"; client-library runtime metrics (`process_*`, `dotnet_*`, `nodejs_*`) exist only if that library is in use; RED/USE/golden-signals are naming *advice*, not enforcement; OpenTelemetry's `service.name` is the one attribute close to load-bearing — get it wrong (as `vote` briefly did) and the service literally doesn't show up under its real name anywhere.

## Real bottleneck found, root-caused, and fixed with measured before/after — the actual payoff of the whole observability build

**Controlled test, not another raw bombing:** reset the queue to 0, ran a small, deliberate 1,000-vote burst (`PHASES = [(20, 1000)]`) specifically to get clean baseline numbers, rather than the earlier uncontrolled 55,000-vote run.

**Before (single `worker` replica, unconditional `Thread.Sleep(100)`):** peak queue 567, steady drain ~9–9.8 votes/s, ~60s to fully drain, longest trace 1m 24s (almost entirely queue wait — `db_write` itself measured 1.59ms, meaning the *work* was never the problem). `vote`'s own p99 latency graph was flagged as near-meaningless during this — its default Prometheus histogram buckets are tuned for typical whole-second web latency, and with `vote` actually responding in single-digit milliseconds, nearly every request falls into one bucket, so `histogram_quantile()` has nothing real to interpolate between and settles near that one bucket's edge (~99ms, suspiciously frozen to the fifth decimal place) — a real, common gotcha with default histogram buckets, not a bug in the query. Filed as a follow-up (custom buckets matched to `vote`'s real latency range) rather than chased immediately.

**The fix:** `Thread.Sleep(100)` was unconditional every loop, whether or not there was work — moved it into the empty-queue branch only, so it never delays a vote that's actually waiting, while still avoiding a busy-spin when idle (preserving the *actual* original intent of the comment, "prevent CPU spike," just applied correctly).

**After (same fix, single replica, same burst): 500× improvement on the exact thing being fixed** — trace duration 1m 24s → 166ms. Worker's own per-vote time unchanged (still ~1.3–8.4ms) — correctly confirming the fix touched the *gap between* votes, not the work itself.

**Scaled up to a genuinely heavy, sustained burst (70,000 votes, 50→100 concurrent) to find the *next* real ceiling — and the result overturned the predicted hypothesis.** Queue climbed to 55K+ and never turned around within the observed window; `worker` **restarted** mid-test (two distinct pod names in the same graph — Deployment `replicas: 1`, so a genuine crash, not a scale-up); one `RPUSH` trace showed 523ms (Redis itself under real strain, not normal); `worker`'s own p99 climbed to ~350ms. Predicted "Postgres connection pool exhaustion" going in — **the evidence didn't support it**: the actual worst-case trace captured mid-burst showed `db_write` at a completely normal 3.75ms, no different from the light-load baseline. Correcting the prediction rather than forcing the data to fit it: the dominant factor was architectural — a single sequential consumer processing one vote at a time has a hard ceiling regardless of how fast each individual step is, against 100 concurrent senders. Redis contention (the `RPUSH` slowness) was real but secondary, plausibly worsened by `worker`'s own queue-length gauge sampling (`LLEN`) on *every* loop iteration, doubling Redis traffic under load for a metric that didn't need per-vote precision — fixed with wall-clock-based sampling (~once/second) instead of per-iteration.

**The actual fix, established as safe all the way back in Phase 0 and never used until now: scaled `worker` horizontally.** Considered a fixed replica count vs. **KEDA** (installed via Helm in `karpenter/`, alongside the other platform prerequisites) — chose KEDA specifically because it closes the loop the whole autoscaling phase left open: `worker` scales on the *real* Redis queue depth (`ScaledObject` with a `redis` trigger, `listName: votes`, `listLength: "50"` per replica), the same underlying mechanism (KEDA creates a normal HPA automatically) as `vote`/`result`'s CPU-based scaling, just fed by a different signal. One real gotcha: KEDA's operator runs in its own `keda` namespace, so it needs Redis's fully-qualified `redis.default.svc.cluster.local` — `worker`'s own hardcoded plain `redis` hostname only works because `worker` itself lives in the same namespace as Redis.

**Rerunning the same heavy burst with KEDA live: queue peaked far lower (~3–5K vs. 55K+) and, critically, actually turned around and drained — the system converges now instead of diverging.** Aggregate throughput reached ~250 votes/s sustained (~25× the original ceiling). Longest trace dropped to 8.18s (from 1m24s–5m42s range in the sleep-only fix, and unbounded/never-recovering before that) — roughly a 10–40× further improvement stacked on top of the first fix. **Honest trade-off surfaced for the first time:** `worker`'s own p99 and `db_write` duration both rose (to ~190–250ms and ~8ms respectively) under concurrent multi-replica load — contention that literally couldn't show up before, since a single sequential worker never touched Redis/Postgres from more than one place at once. This is a real, expected shape for this class of fix (traded some per-vote latency for a large aggregate throughput gain), and it means the original "exhaust the DB pool" scenario hasn't disappeared — it's been pushed one layer further out, now genuinely reachable by scaling `worker` replicas harder under sustained load, with real concurrent writers this time instead of one throttled loop.

**Mid-load-test operational lesson, from actually hitting it live:** the base node group's `desired_size = 1` meant Karpenter's reactive node launch was the *only* thing standing between the cluster and running out of capacity — and a new EC2 node's boot-to-Ready time (real `RunInstances` → OS boot → kubelet → VPC CNI IP-prefix allocation → Ready conditions, commonly 60–180s) has a genuine physical floor no Karpenter setting removes. Bumped `desired_size` to 2 as a standing buffer so a first burst never has to wait on a cold launch at all. Considered and explicitly rejected, for now, a Karpenter-specific alternative (a low-priority "placeholder" Deployment using `registry.k8s.io/pause` pods + a negative `PriorityClass`, so Kubernetes preemption hands freed capacity to real pods instantly while Karpenter launches a replacement node in the background) — real, standard pattern, but for this project's single-instance-type setup it costs the same as `desired_size = 2` (one continuously-running extra node either way) while adding real complexity Karpenter's flexible instance-type selection doesn't actually buy here. Filed away as the correct answer if the NodePool ever needs to choose between genuinely different instance types under pressure. Also distinguished a "bombing" test (all-at-once, the right tool for finding absolute breaking points, which is what's been run so far) from a "ramp" test (gradual concurrency increase, needed to properly test whether the autoscaling machinery keeps pace *while* a spike is happening, rather than testing an instant cliff) — noted as a different, complementary exercise for later, not yet built.
